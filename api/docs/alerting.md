# Alerting

What in the API is worth waking someone for, and how to tell. Companion to
[`logging-conventions.md`](./logging-conventions.md): that document says how to write a log line, this one says
which lines an alert rule is built on.

---

## 1. Approach

- **Alerts are rules over log events.** The API already writes structured JSON with a stable `event` field
  (conventions §5). CloudWatch Logs evaluates the rules in §3 against those lines and emails the result (§6). The
  API holds no alerting code and no vendor SDK, and nothing here depends on the choice of platform.
- **Error tracking is a separate, later decision.** Grouping and triaging unexpected 5xx (stack traces, release
  tagging) is a different tool for a different job. Until it exists, the `request.unhandled_error` rule below is
  the coarse substitute.
- **A rule matches on `event`, never on the message.** Messages are for people and may be reworded. Where one
  event is logged at more than one level, the rule also matches on `level` or on a field; the table says which.
- **The event names are a contract.** Every name in §3 lives in
  [`src/common/logging/alert-events.constants.ts`](../src/common/logging/alert-events.constants.ts), the code that
  logs it references the constant, and a unit test pins the strings. Renaming one means changing the alert rule
  and this document in the same change. The count fields the rules read (`failed`, `abandoned`, `expired.failed`,
  `completed`) are part of the same contract.
- **Where the urgency depends on the content, the line says so.** Such events carry `severity` (`page` or
  `ticket`, `ALERT_SEVERITY` in the same file), and the rule routes on it. The business rule behind it (which
  escalation reasons page) stays in code, pinned by the same unit test.
- **Alert lines name things, not people.** Alerts are copied into whatever ticketing, mail or paging system
  consumes them, outside the log platform's access control. A moderation alert carries the `reportId`, `eventId`,
  `reason`, `queue` and `escalationReasons`, never the reporter, the reported member or the photo. Those stay on the
  audit lines (`report.created`, `report.moved_to_platform`), which the person who acts on the alert reads by
  `reportId` inside the log platform.

### Scheduler heartbeats

A cron job that stops firing logs no error, so there is nothing to match on. Every `@Cron` handler therefore runs
through [`runScheduledJob`](../src/common/scheduling/run-scheduled-job.ts), which writes exactly one line per run:

- `<job>.run_completed` at `info` when the run returned, **including a run that found nothing to do**, with
  `durationMs` and the job's result counts;
- `<job>.run_failed` at `error` with `err` and `durationMs` when it threw.

The alert is on the **absence** of `run_completed` for longer than twice the job's interval. A disabled job logs
neither line, so a heartbeat rule belongs only in an environment where the job is switched on.

| Job                          | Heartbeat event                                 | Interval     | Enabled by                                      |
| ---------------------------- | ----------------------------------------------- | ------------ | ----------------------------------------------- |
| Account deletion reconcile   | `user.account.deletion_reconcile.run_completed` | hourly       | `ACCOUNT_DELETION_RECONCILER_ENABLED=true`      |
| Pending photo cleanup        | `photo.pending_cleanup.run_completed`           | hourly       | on unless `PHOTO_PENDING_CLEANUP_ENABLED=false` |
| Orphaned S3 object reconcile | `storage.orphan_reconcile.run_completed`        | daily, 03:00 | `PHOTO_ORPHAN_RECONCILER_ENABLED=true`          |
| Stale report check           | `report.stale_check.run_completed`              | hourly       | always on                                       |
| Gallery close                | `event.gallery_close.run_completed`             | hourly       | `GALLERY_CLOSE_ENABLED=true`                    |
| Evidence job                 | `report.evidence_job.run_completed`             | daily, 04:00 | `MODERATION_EVIDENCE_JOB_ENABLED=true`          |
| Photo hash backfill          | `photo.hash_backfill.run_completed`             | hourly       | `PHOTO_HASH_BACKFILL_ENABLED=true`              |
| Upload screening             | `photo.screening.run_completed`                 | every minute | `MODERATION_SCREENING_ENABLED=true`             |
| Notification send            | `notification.send.run_completed`               | every minute | on unless `NOTIFICATIONS_SENDER_ENABLED=false`  |
| Notification receipts        | `notification.receipts.run_completed`           | every 15 min | on unless `NOTIFICATIONS_SENDER_ENABLED=false`  |
| Notification retention       | `notification.retention.run_completed`          | daily, 05:00 | always on                                       |

The names are per job rather than one shared `scheduler.run_completed` with a `job` field: the failure events
already existed as `<job>.run_failed` and must not change, the pair reads as one thing, and the names keep the
`<domain>.<entity>.<action>` shape of every other event. One rule can still cover all jobs by matching the
`.run_failed` suffix.

## 2. Severity

- **Page**: someone is locked out, data is not being deleted that must be, a safety net is gone, or a legal
  deadline is running (child safety, intimate images). Act now.
- **Ticket**: money or quota is leaking, or a job is degraded but still running. Act in working hours.

## 5. Adding or changing an alert

1. Add the event name to `ALERT_EVENTS` and to the pinned test next to it, and log it through the constant.
2. Add a row to §3 with a condition and an action. An alert nobody knows how to act on is noise.
3. Add the rule to [`infra/moderation-alerts.tf`](../../infra/moderation-alerts.tf) (§6), in the same PR or in
   one that lands before the event ships.
4. Never rename an event in §3 without changing its rule there in the same release.

## 6. How alerts are delivered

The API runs on ECS through Copilot ([`api/copilot/api/manifest.yml`](../copilot/api/manifest.yml)), so its lines
are already in CloudWatch Logs, in the group Copilot creates for the service: `/copilot/everglow-<env>-api`. The
rules in §3 are CloudWatch metric filters on that group with an alarm each, in
[`infra/moderation-alerts.tf`](../../infra/moderation-alerts.tf). Saved Logs Insights queries and a dashboard
for the same group live in [`infra/api-logs.tf`](../../infra/api-logs.tf); both files share
`api_log_group_name` and the short name in [`api-log-group.tf`](../../infra/api-log-group.tf). Every alarm
publishes to the same SNS topic as the photo privacy alerts and the image processor's DLQ alarm
(`everglow-security-alerts-dev`, [`photo-privacy.tf`](../../infra/photo-privacy.tf)), which emails the addresses
in `alert_emails`. No vendor and no code in the API.

- **Page or ticket is in the alarm name**, `everglow-<env>-api-page-…` or `…-ticket-…`, so the email's subject says
  how fast to act. Until a paging service is chosen both arrive as email; subscribing a phone or a pager to the
  topic later needs no change to the rules.
- **The email carries no user text.** The description is written in the Terraform: what the alarm means, the §3
  event to read about, and a console link to the matching lines in the log group. The ids are read there, inside
  the log platform's access control, never in the mail.
- **Rules match the `event` field**, and `level` (pino writes it as a number, `50` for error) or another field
  where §3 says so. Where the urgency depends on the content, the page rule also matches `severity = "page"`.
- **Heartbeats exist only where the job runs.** `api_jobs_enabled` in `terraform.tfvars` lists the optional jobs
  the environment switches on; keep it in step with that environment's `*_ENABLED` variables in the manifest. A
  job switched on there that logs a `*.disabled` line at boot also gets an alarm on that line, so turning it off
  by mistake is caught on the next deploy. The stale report check always runs and is always watched.
- **Where a metric cannot say what §3 says**, the rule is the nearest count: `event.gallery_close.failed` alarms on
  three hourly runs in a row with a failure, not on the same `eventId`; the `sensitive` rate limit rule counts
  lines, not distinct users. The comment on each rule says so.
- **Cost** is one custom metric and one alarm per rule, about $0.40 a rule a month.

### Applying

The log group belongs to Copilot's stack, so Terraform reads it and never creates it. In a new environment:

1. `copilot svc deploy --env <env>` creates the log group (and sets its retention from the manifest).
2. Set `api_log_group_name` and `api_jobs_enabled` in `infra/terraform.tfvars`, then `terraform plan` and
   `terraform apply` from `infra/`. Until the group exists, the plan holds no API alerts and warns
   (`check "api_log_group_exists"`) instead of failing.

A heartbeat alarm can fire once right after it is created, because its metric has no history yet; it returns to
OK after the job's next run. To prove delivery end to end, force one alarm and wait for the email:

```sh
aws cloudwatch set-alarm-state --alarm-name everglow-staging-api-ticket-report-stale \
  --state-value ALARM --state-reason "Delivery test"
```

The alarm returns to its real state at its next evaluation. Deleting the service with Copilot deletes the log
group and the filters with it; the next `terraform apply` after a redeploy recreates them.
